## Context

<!-- SECTION:CONTEXT:BEGIN -->
claude.ai custom connectors sign in with OAuth; the HTTP transport of decision-27 knows only static bearer tokens. Decision-9 left the identity provider for this milestone open on purpose. The owner (2026-11-22) wants no specific provider: the server should follow pvliesdonk/paperless-mcp and use FastMCP's generic `OIDCProxy`, configured only through environment variables, as an optional layer on top of the bearer tokens, so that claude.ai signs in through OIDC while Claude Code keeps its bearer token, with one shared Paperless token as today (per-user credentials are PLMCP-37). FastMCP 4.2 combines an auth server with token verifiers in `MultiAuth` (`docs/vendor/fastmcp/docs/servers/auth/multi-auth.mdx`). The layer adds OAuth routes, opens the server's own origin to its consent form and lets the server start without bearer tokens: all three change rules of decision-27, so this decision replaces it. Starting without tokens and writing OAuth state to a mounted directory also contradict three statements of decision-28 (the container image), so this decision replaces that one too.
<!-- SECTION:CONTEXT:END -->

## Decision

<!-- SECTION:DECISION:BEGIN -->
**Supersedes decision-27.** Everything in decision-27 is carried over unchanged (the entrypoint, the loopback classification, the token format and constant-time verification, the strict host and origin guard and its 421/403 answers, no CORS, the defence in depth of the unauthenticated loopback mode, the explicit FastMCP options, no trailing-slash redirects and no WebSockets, the request id and the request log without query, headers, tokens or bodies, the body limit, no path parameter over HTTP, its consequences and enforcement), except:

**Supersedes decision-28.** Everything in decision-28 is carried over unchanged (the Dockerfile stages, digest pins and Renovate comments, the numeric non-root user, `.dockerignore`, the entrypoint bound to 0.0.0.0, the TCP health check, the image workflow with its scan, smoke test, ancestor check and digest-first publishing, no publishing by hand, its consequences and enforcement), except exactly these three statements:

- "the server writes nothing" becomes: the server writes nothing unless `PAPERLESS_MCP_OIDC_STORAGE_DIR` is set; then it writes only there, a directory the operator mounts (owned by uid 10001). The image still works with `--read-only`, `--cap-drop ALL` and `no-new-privileges`.
- "decision-27's refusal applies unchanged" becomes: the startup refusal of this decision applies (decision-27's, with the OIDC layer counting as authentication).
- "the container does not start until `PAPERLESS_MCP_HTTP_AUTH_TOKENS` and `PAPERLESS_MCP_HTTP_ALLOWED_HOSTS` are set" becomes: the container does not start until authentication (`PAPERLESS_MCP_HTTP_AUTH_TOKENS`, the complete OIDC layer, or both) and `PAPERLESS_MCP_HTTP_ALLOWED_HOSTS` are set.

For the HTTP transport:

- **The OIDC layer is optional and off by default.** It is on when any `PAPERLESS_MCP_OIDC_*` variable is set (`settings.OidcSettings`; empty values count as unset). Five are required: `PAPERLESS_MCP_OIDC_CONFIG_URL` (the provider's discovery document), `PAPERLESS_MCP_OIDC_CLIENT_ID`, `PAPERLESS_MCP_OIDC_CLIENT_SECRET` (`SecretStr`), `PAPERLESS_MCP_OIDC_BASE_URL` (the public origin of this server) and `PAPERLESS_MCP_OIDC_JWT_SIGNING_KEY` (`SecretStr`, at least 32 characters). Optional: `PAPERLESS_MCP_OIDC_STORAGE_DIR` and `PAPERLESS_MCP_OIDC_ALLOWED_REDIRECT_URIS`. The names keep the server's `PAPERLESS_MCP_` prefix (design §5.8) with an `OIDC_` group of their own, next to `HTTP_`, because the layer has its own all-or-nothing rule and the names follow the parameters of `OIDCProxy` (`config_url`, `client_id`, `client_secret`, `base_url`, `jwt_signing_key`) as pvliesdonk/paperless-mcp does. The discovery URL and the base URL must be https, plain http only on a loopback address; the base URL is an origin without path, query or credentials.
- **Startup refusal** (`app.check_startup`): the server needs authentication, which is now `PAPERLESS_MCP_HTTP_AUTH_TOKENS`, the OIDC layer, or both; without either the refusal and the unauthenticated loopback flag work as before. An OIDC layer with some but not all required variables refuses to start and names the missing ones, even when bearer tokens are set. With the layer on, the host of the base URL must be a loopback name or in `PAPERLESS_MCP_HTTP_ALLOWED_HOSTS`, a storage directory must be a writable directory, and the discovery document must be readable at startup (`app.oidc_proxy`): an unreachable provider, a malformed document and a proxy FastMCP cannot build from it each get their own message with the error type only. A discovery URL or base URL carrying credentials is refused, so no message prints them. Remote binds still need allowed hosts.
- **Authentication** (`app.authenticator`): bearer tokens alone stay `StaticBearerVerifier`. With the OIDC layer it is FastMCP's `MultiAuth`: the `OIDCProxy` first, then the bearer verifier (named `static-bearer`) if tokens are set, `required_scopes=[]` outside (the proxy enforces the `openid` scope on its own sessions; bearer tokens carry no scopes). The proxy verifies the provider's **ID token** (`verify_id_token=True`, audience the client id, keys from the discovery document's JWKS), because every OIDC provider issues one as a signed JWT while access tokens may be opaque (Google) or meant for another audience. It asks the provider for the `openid` scope. The consent page stays on (`require_authorization_consent=True`), PKCE is forwarded, dynamic client registration and CIMD are offered, and clients may register only the callbacks in `PAPERLESS_MCP_OIDC_ALLOWED_REDIRECT_URIS` (default: claude.ai's `https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback` (Anthropic has announced the callback may move there; both domains are Anthropic's), `http://localhost:*` and `http://127.0.0.1:*`; entries are https URLs or loopback http, a `*` only for the port or in the path). Tools see one shared Paperless token whoever signed in, as before.
- **Keys and storage:** the signing key is required instead of FastMCP's key derived from the client secret, which FastMCP calls fit for development only; it signs the tokens the server issues and, through a Fernet key stretched from it with PBKDF2 (FastMCP's `derive_jwt_key` for low-entropy material, as FastMCP treats a string signing key), encrypts the stored state; a value that no longer decrypts is a miss, so a new key makes clients register again. Client registrations, sessions and upstream tokens live in memory, at most 10 000 entries per collection (the oldest are dropped), unless `PAPERLESS_MCP_OIDC_STORAGE_DIR` names a directory: then in encrypted files there (`FileTreeStore` with FastMCP's V1 key and collection sanitising, so any key stays inside its collection directory, in `FernetEncryptionWrapper`). FastMCP's default disk store is never used (it lives under a home directory the container lacks and follows `FASTMCP_HOME`). Without a storage directory a restart signs every OIDC client out; bearer clients are not affected.
- **Routes:** without the layer, still only the MCP endpoint. With it, FastMCP's OAuth routes as well, and nothing else: `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource<path>`, `/authorize`, `/token`, `/register`, `/consent` and `/auth/callback` (the callback the provider must allow is `<base URL>/auth/callback`). The 401 challenge of the MCP endpoint points to the protected resource metadata.
- **Origins:** with the layer, the origin of the base URL (`app.public_origin`: without a port only when the port is its scheme's default, 443 for https, 80 for http) is the one browser origin allowed besides the loopback rules, so the consent form can post to its own server (behind a TLS proxy the request arrives as plain http, and the guard's same-origin fallback would not match). Every other origin still gets 403, also on the preflight requests of the OAuth routes, so no cross-origin access is granted.
- **Unauthenticated loopback guard:** applies only while neither tokens nor the OIDC layer are configured.

## Consequences

<!-- SECTION:CONSEQUENCES:BEGIN -->
- Any OIDC provider works (Authentik, Keycloak, Google, Auth0, ...); the README shows Authentik. The provider must issue ID tokens and allow `<base URL>/auth/callback`; it is contacted at every start, so a provider that is down stops the start (a container restart policy retries).
- claude.ai and Claude Code can use one server at the same time: claude.ai through OIDC, Claude Code with its bearer token. Whoever signs in through the provider uses the shared Paperless token; restricting who may sign in is the provider's job (application bindings or groups). Per-user Paperless credentials remain PLMCP-37.
- The container stays read-only: without a storage directory nothing is written; with one, only the mounted directory is. In-memory state means reconnecting the claude.ai connector after each restart.
- `/register` and `/authorize` need no authentication, and each call stores an entry (a registration, a transaction). In memory the cap bounds the growth, but a flood can push real registrations out (claude.ai then registers again). On disk nothing bounds it: FastMCP does not cull a store it did not create, so expired entries stay until overwritten. Rate-limit `/register` and `/authorize` at the reverse proxy.
- FastMCP logs the provider's subject when it rejects a token: personal data in the log (an identifier, no secret).
- Every request re-checks the provider's ID token; once it expires (often an hour) the proxy refreshes upstream, which works only if the provider returns a fresh ID token on refresh. Otherwise the client signs in again.
- Rotating the signing key or changing the storage directory signs every OIDC client out. Rotating the client secret does not.
- The Dockerfile and the image workflow are unchanged.
- Whether claude.ai connects against a real provider is verified manually by the owner (PLMCP-36): it cannot be tested without a public URL.
<!-- SECTION:CONSEQUENCES:END -->

## Enforcement

- `tests/test_oidc.py` (marker decision-31): with a stub OIDC issuer on a loopback port (`tests/oidc_issuer.py`: discovery, authorization, token endpoint checking secret and PKCE, JWKS, opaque access tokens) and a scripted browser on FastMCP's OAuth client, the full flow signs in and lists the tools; the provider is asked for `openid` with S256 PKCE and the base URL's callback; bearer tokens work beside it; the claude.ai callback registers and reaches the consent page, a foreign callback is refused at registration and authorization; a consent post from another origin is refused, the server's own origin passes; the OAuth routes refuse cross-origin preflights; the exact route set; the 401 challenge; registrations survive a restart with a storage directory, encrypted, and are forgotten without one; the startup matrix (none, bearer, OIDC, both), incomplete settings, the base URL host, the storage directory and an unreachable issuer refuse to start; no secret, code or token reaches the log at INFO; an ID token with the wrong audience or issuer, an expired one, an unknown key id or a bad signature signs nobody in; an OIDC-only app answers 401 without a token, to a bearer-shaped token and to a token shaped like its own but signed with another key; odd client ids get a clean 400 with a storage directory and file-store keys stay in their collection; the storage key is the PBKDF2-stretched one; the in-memory store is capped; the public origin keeps a non-default port.
- `tests/test_settings.py` (marker decision-31): the OIDC variables, empty values as unset, the list of missing variables, secrets masked in `repr`, https or loopback URLs, the base URL as an origin, the signing key length, the redirect allowlist.
- `tests/test_cli.py` (marker decision-31): incomplete or invalid OIDC settings end the process with exit code 1, naming the variables without echoing secrets; the OIDC layer alone serves.
- Everything decision-28 lists under Enforcement (`tests/quality/test_container.py` with its marker decision-28, `scripts/image_smoke.sh`) still runs unchanged.
- Everything decision-27 lists under Enforcement (`tests/test_app.py` with its marker decision-27, `tests/test_settings.py`, `tests/test_cli.py`, `tests/tools/test_registry.py`) still runs unchanged.
- A real claude.ai connector against a real provider is checked manually by the owner (manual review).
